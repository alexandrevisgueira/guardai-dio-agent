Análise de AppSec: arquivo lab/app.py

1. FALHA IDENTIFICADA
  - Localização: lab/app.py, linha 31, na função login().
  - Problema: SQL Injection (CWE-89 / OWASP A03:2021 - Injection).
  - Causa raiz: concatenação direta de entradas do usuário na string SQL:
    query = "SELECT id, usuario FROM usuarios WHERE usuario = '" + usuario + "' AND senha = '" + senha + "'"

2. COMO A FALHA É EXPLORADA
  - Bypass de autenticação:
    Se a entrada para o campo 'usuario' for:
      admin' --
    E no campo 'senha' for digitado qualquer valor, a consulta executada no SQLite vira:
      SELECT id, usuario FROM usuarios WHERE usuario = 'admin' --' AND senha = '...'
  - O trecho '--' inicia um comentário no SQL, anulando a verificação de senha. O banco executa a busca apenas pelo usuário 'admin' e autoriza o login sem que a senha seja validada.

3. TÉCNICA MITRE ATT&CK
  - Técnica: T1190 - Exploit Public-Facing Application
  - Descrição: O atacante explora uma vulnerabilidade em uma aplicação exposta (login web/API) para burlar autenticação ou interagir diretamente com o banco de dados.

4. AVALIAÇÃO DE RISCO
  - Impacto: Alto (quebra confidencialidade e integridade ao permitir acesso não autorizado a contas de terceiros).
  - Probabilidade: Alta (falha trivial de ser identificada e explorada).
  - Severidade: Crítica (Impacto Alto x Probabilidade Alta).

5. REESCRITA DO CÓDIGO (COMO CORRIGIR)
  - Princípio: separação entre código SQL e dados do usuário usando consultas parametrizadas (prepared statements). O driver do banco garante que os caracteres digitados sejam tratados estritamente como texto, impedindo que alterem a estrutura do SQL.

  Código da função login() corrigida:

  def login(conn, usuario, senha):
      cur = conn.cursor()
      # O uso de '?' delega ao SQLite a separação segura entre comando e dado
      cur.execute("SELECT id, usuario FROM usuarios WHERE usuario = ? AND senha = ?", (usuario, senha))
      return cur.fetchone()

  Medidas complementares de defesa em profundidade:
    1. Guardar senhas com hash e salt (ex: PBKDF2 ou bcrypt) em vez de texto puro.
    2. Usar comparação de hash em tempo constante (hmac.compare_digest).
    3. Remover mensagens e logs de debug que exponham comandos internos do banco.

  Obs: No repositório, o arquivo lab/app_seguro.py contém a implementação completa com armazenamento seguro de senhas por hash PBKDF2. Rodando 'python lab/testar_injecao.py' você pode validar a diferença de comportamento entre o app.py vulnerável e o app_seguro.py.
